# ADR 0003: The CDK is a toolbox, not a gatekeeper

The Connector CDK is vendor-neutral machinery a connector uses — the
capability contract, transports, the type-map engine, the secrets seam —
never a central engine a connector must route through. Vendor-specific
logic (a database's driver, its type-map mappings, its dialect SQL) lives
in the connector, generated by the connector-builder plugin, and runs on
an unchanged CDK.

## Why not a gatekeeper

The alternative — DB-specific logic living in the shared library — puts
an engineer in the loop for every new database: a brand-new system (say
Clickhouse) would not run until someone updated the library. That breaks
the platform's core promise, self-service authoring: a user describes a
system and a plugin builds the connector, with no engineer in the
critical path. A CDK that gatekeeps new databases behind engineering
capacity contradicts the reason the platform exists.

The test that keeps this honest: **would this code change when you add
Clickhouse?** If yes, it is vendor-specific and belongs in the connector.
If no, it is generic and can live in the CDK. The CDK holds the operation
Protocols, the transport families, the `SecretsResolver` seam, the
type-map *mechanism* (not any mappings), and optional reusable building
blocks like a generic SQL base a connector may subclass — every one of
those passes the test.

## Why not "the engine owns drivers and exposes operations"

The CDK is also not folded into either runtime that consumes it. Making
the engine own drivers and expose operations would tie a
latency-sensitive control-plane call (list schemas, create a table) to
the full streaming runtime's weight, and would stop the engine from
shipping as a lean, self-contained Docker image. A shared, independently
installable CDK lets a synchronous control-plane process and the
streaming engine both consume the same connector code as thin clients —
same code, two front doors — without either owning it.

## Where the CDK lives, and how a connector reaches it

The CDK lives in the engine repo (`cdk/`) as a distinct,
independently-installable package, not a separate repo: the engine
already held the richer ADBC/async driver layer, so extracting it in
place was the lowest-friction move — an in-repo factoring of code the
engine already had, not new territory.

Connector *code* (`connector.py` + deps) is distributed with its JSON
definition in the same per-connector repo, one repo per connector, versioned
together by git tag. This reuses the repo-per-connector model already in
place rather than standing up a separate package index.

MSSQL is a first-class connector module — a proper driver + type-map, not
an optional install extra — because users expect SQL Server support, and
dropping it to keep the CDK's core install lean would be a regression, not
a simplification.
